## 1. 지금까지 무슨 일이 있었나

우리는 Visual Studio Code에서 html/css/js로 홈페이지 화면을 만들어왔습니다. 그런데 내 컴퓨터 안에서 파일을 열어보는 것과, **전 세계 누구나 인터넷 주소로 접속해서 보는 것**은 완전히 다른 이야기죠. 후자를 가능하게 하려면 "웹 호스팅"이 필요합니다.

**웹 호스팅이란?** 우리 홈페이지 파일을 24시간 켜져 있는 컴퓨터(서버)에 올려두고, 그 컴퓨터를 인터넷 주소로 누구나 찾아올 수 있게 해주는 서비스입니다. 저번 주 회의에서 한국 업체인 **Cafe24**의 node.js 호스팅을 쓰기로 결정했었고, 8/11에 팀장이 다음 작업을 완료했습니다.

- Cafe24 서버 환경 설정
- 데이터베이스(DB) 서버 구축 및 연동
- 지금까지 만든 홈페이지 코드를 실제로 그 서버에 올리는 것(배포)까지 완료

그 결과, 이제 **http://teamlogic.cafe24app.com** 이라는 주소가 생겼습니다. 이 주소는 전 세계 어디서든, 누구나, 24시간 접속할 수 있습니다. 우리가 자던, 컴퓨터를 끄던 상관없이 이 사이트는 계속 켜져 있습니다.

오늘부터는 각자 담당한 부분을 이 서버 위에서 실제로 개발/운영해나가는 단계입니다.

## 2. 웹사이트는 왜 세 부분(프론트/백엔드/DB)으로 나뉘나

식당에 비유하면 이해하기 쉽습니다.

| | 식당 비유 | 우리 프로젝트 |
|---|---|---|
| **프론트엔드** | 손님이 보는 홀, 메뉴판, 테이블 | 사용자 눈에 보이는 화면 (버튼, 글씨, 색깔, 레이아웃) |
| **백엔드** | 주방에서 요리하고 서빙 순서를 정하는 로직 | "로그인해도 되는지 확인", "게시글 저장해줘" 같은 처리 로직 |
| **데이터베이스(DB)** | 냉장고/식자재 창고 | 회원 정보, 게시글, 일정 같은 실제 데이터를 저장하는 곳 |

손님(사용자)이 웹사이트 버튼을 누르면 → **프론트엔드**가 그 요청을 받아서 → **백엔드**에게 이거 처리해달라고 전달하고 → 백엔드가 필요하면 **DB**에서 데이터를 꺼내오거나 저장한 뒤 → 다시 프론트엔드에 결과를 돌려줘서 화면에 보여주는 흐름입니다.

그래서 우리 팀도 이 세 역할대로 나뉘어 있는 겁니다: **프론트엔드팀 / 백엔드팀 / DB팀**.

## 3. 폴더 구조와 팀별 담당 영역

프로젝트 폴더는 이렇게 생겼습니다. 각 파일/폴더를 누가 관리하는지 표시했습니다.

```
logic-web/
├── main/
│   ├── html/     ← 프론트엔드팀 담당
│   ├── css/      ← 프론트엔드팀 담당
│   ├── js/       ← 프론트엔드팀 담당 (화면 동작 스크립트)
│   └── assets/   ← 프론트엔드팀 담당 (이미지 등)
├── server/
│   ├── server.js     ← 백엔드팀 담당 (API 로직 전부 이 한 파일 안에 있음)
│   └── db/
│       └── schema.sql ← DB팀 담당 (테이블 설계도)
├── web.js            ← 백엔드팀 (거의 건드릴 일 없음, server.js를 불러오기만 함)
├── package.json      ← 백엔드팀 (필요한 라이브러리 목록)
├── .env / .env.example ← DB팀 (실제 비밀번호가 들어가는 파일)
└── README.md          ← 지금 보고 있는 이 문서
```

**한 줄 요약**: 화면에 보이는 건 다 프론트엔드팀 파일(`main/` 폴더), 뒤에서 돌아가는 처리 로직은 백엔드팀 파일(`server/server.js`), 데이터 저장 구조는 DB팀 파일(`server/db/schema.sql`)입니다.

## 4. 프론트엔드팀 — 알아야 할 것 / 신경 써야 할 것

### 알아야 할 것

- 담당 파일은 `main/html/*.html`, `main/css/*.css`, `main/js/*.js` 입니다.
- 파일 이름 규칙: `home.html`은 `css/home.css`, `js/home.js`랑 세트로 묶여 있습니다. 새 페이지를 만들 땐 이 세 파일을 같이 만드세요.
- 서버를 켤 필요 없이, html 파일을 그냥 브라우저에서 더블클릭해서 열어도 화면 확인이 대부분 가능합니다.
- 로그인처럼 서버와 통신하는 화면을 테스트하려면 `npm start`로 로컬 서버를 띄워야 합니다 (7번 항목 참고).

### 신경 써야 할 것

- 다른 페이지(`home.html` 등)를 열어보고 상단 메뉴바, 로그아웃 버튼 같은 **공통 구조는 그대로 복사**해서 시작하세요. 페이지마다 디자인이 제각각이면 나중에 통일하는 게 훨씬 힘듭니다.
- 백엔드팀이 만든 API를 호출할 땐 주소를 **절대 `http://localhost:3000`처럼 직접 쓰지 마세요.** `/api/login`처럼 앞에 도메인 없이 상대경로로 쓰세요. 그래야 우리 컴퓨터에서 테스트할 때도, 실제 배포된 사이트에서도 둘 다 정상 작동합니다.

## 5. 백엔드팀 — 알아야 할 것 / 신경 써야 할 것

### 알아야 할 것

- API(백엔드 로직)는 전부 `server/server.js` 한 파일에 있습니다. 지금은 로그인(`/api/login`) 하나만 구현돼 있습니다.
- 새 기능(예: "공지사항 목록 가져오기" API)을 만들 땐, 기존 `/api/login` 코드를 복사해서 패턴을 그대로 따라 하면 됩니다.
- **실제 운영 DB는 백엔드팀이 직접 접속할 수 없습니다.** Cafe24 서버 내부망에서만 접속되는 주소라서 그렇습니다. 대신 아래처럼 내 컴퓨터에 "개발용 DB"를 따로 설치해서 씁니다.

### 로컬 개발 DB 만들기 (최초 1회)

```bash
# Mac 기준
brew install mysql
brew services start mysql
mysql -u root -e "CREATE DATABASE logic_web_dev;"
mysql -u root logic_web_dev < server/db/schema.sql
```

그 다음 프로젝트 루트에 `.env` 파일을 만들고(`.env.example`을 복사) 이렇게 채우세요:

```
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=root
DB_PASSWORD=(로컬 mysql 비밀번호, 보통 비어있음)
DB_NAME=logic_web_dev
```

이제 `npm start`로 서버를 켜면 내 컴퓨터 안의 개발용 DB에 붙어서 자유롭게 개발/테스트할 수 있습니다. **이건 진짜 회원 정보가 아니라 연습용 가짜 DB라서 마음대로 만들고 지워도 안전합니다.**

### 신경 써야 할 것

- DB 테이블 구조(컬럼 추가 등)가 필요하면 직접 운영 DB를 못 건드리니, DB팀에게 "이런 컬럼/테이블 필요해요"라고 요청하세요.
- 비밀번호 등 민감한 값은 코드에 절대 직접 적지 말고 `.env`에서 불러오세요 (`process.env.XXX` 형태). 이미 그렇게 되어 있으니 이 패턴을 유지하면 됩니다.

## 6. DB팀 (+팀장) — 알아야 할 것 / 신경 써야 할 것

### 원칙

**실제 운영 DB 비밀번호와 배포 키는 DB팀과 팀장만 알고 있습니다.** 다른 팀원에게 공유하지 마세요. 필요하면 DB팀에게 "이 값 좀 확인해줘"라고 요청하는 방식으로 진행합니다.

### 알아야 할 것

- 운영 DB 주소는 `10.0.0.1`이고, Cafe24 내부망에서만 접속됩니다. A클래스 사설 IP 대역입니다. 따라서 "내부 망"에서만 접속이 되고 외부에서는 접근이 안 됩니다.
- 대신 서버에 미리 만들어둔 **`/admin/run-sql`** 이라는 API로 SQL을 실행할 수 있습니다.

```bash
curl -X POST http://teamlogic.cafe24app.com/admin/run-sql \
  -H "Content-Type: application/json" \
  -H "x-admin-key: (실제 ADMIN_KEY)" \
  -d '{"sql":"SELECT * FROM users"}'
```

- 테이블 구조는 `server/db/schema.sql`에 정의되어 있습니다 (users, notices, board_posts, schedules, gallery_folders, gallery_photos 6개).

### 신경 써야 할 것

- `x-admin-key` 값은 DB 비밀번호와 동급으로 취급합니다.
- 스키마를 바꿀 땐 `server/db/schema.sql` 파일도 같이 수정해서 커밋해두세요. 그래야 나중에 팀원이 로컬 개발 DB를 새로 만들 때 최신 구조로 만들어집니다.
- 배포(실제 사이트에 반영) 절차는 아래 8번 항목을 참고하세요.

## 8. 배포 절차

프론트/백엔드팀이 GitHub(`main` 브랜치)에 올린 코드를, 실제 사이트(Cafe24)에 반영하는 절차입니다.

이 저장소는 원격 저장소가 2개입니다.

| 원격 이름 | 용도 |
|---|---|
| `origin` (GitHub) | 지금까지 우리가 github 들어가면서 봤던, 팀 전체가 코드를 공유하는 곳. `main` 브랜치만 사용 |
| `cafe24` | 실제 서버에 배포하는 곳. 여기다 git push 하면 코드가 서버로 올라가는데, 실제로 사이트에 반영되려면 아래처럼 앱을 재시작해줘야 합니다. |

```bash
git checkout deploy/cafe24
git merge main          # main의 최신 변경사항을 배포 브랜치로 가져오기
git add -A && git commit -m "deploy: ..."
GIT_SSH_COMMAND="ssh -i ~/.ssh/id_rsa -o IdentitiesOnly=yes" git push cafe24 deploy/cafe24:master
```

push 후 **Cafe24 콘솔 → 앱 생성/관리 → `teamlogic` 앱을 중지했다가 다시 실행**해야 실제로 반영됩니다.

⚠️ **`deploy/cafe24` 브랜치는 절대 GitHub(`origin`)에 push하면 안 됩니다.** 실제 DB 비밀번호가 들어있어서 이 브랜치가 공개되면 우리 DB가 통째로 뚫립니다.
